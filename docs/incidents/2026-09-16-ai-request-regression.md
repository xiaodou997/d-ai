## 1. 运行状态告警：确定的 v18 缺陷

代码：`internal/ai/routing/availability.lua`、`internal/ai/routing/availability.go`、`internal/ai/transport/upstream_stability.go`。

1. Lua 初始化 `recent_trips={}`；Redis cjson 将空表持久化为 JSON 对象 `{}`。
2. `snapshot()` 对返回数据做了空数组规整，但 `save()` 存储的原始状态没有规整。
3. `List()` 先 GET 原始数据，再反序列化成 `AvailabilitySnapshot`；Go 的 `RecentTrips []int64` 无法接收对象。
4. 实际错误为 `json: cannot unmarshal object into Go struct field AvailabilitySnapshot.recent_trips of type []int64`。
5. 稳定性列表及单账号详情共用全局状态列表；任一这样的记录会让全部账号状态变为 unknown。
6. `Resume()` 同样先调用 `List()`，因此“立即恢复试用”无法修复该错误。

本地 Redis PING 成功。初始列表正常，一次真实请求之后，HTTP 稳定性接口返回 200，但 19/19 个账号出现 `state_error`。独立真实 Redis 用例：Acquire → Complete(success) → Read 成功 → List 失败，已复现。

**影响边界：**这是全局状态展示和恢复操作故障，不是已证实的所有业务请求阻断原因。正常调度 `Read()` 经过 Lua snapshot，独立用例成功。真正的 Redis 连接错误等仍会让调度返回 503 `availability_state_unavailable`，但本次没观测到该情况。

修复方向：统一持久化/读取 schema，并兼容现存 `{}` 数据；不能只修前端提示，也不应清空全部 Redis。状态接口应按资源隔离故障，保留可追踪的后台错误原因。

## 2. 上游失败与冷却：已观察到放大效应

代码：`serving/classifier.go`、`serving/availability.go`、`routing/availability.lua`。

通用非认证 403 被归类为 `model_error`，模型/操作范围立即冷却，初始 30 秒；后续失败退避至最多 5 分钟。401/明确认证错误则为账号认证范围、30 分钟。恢复阶段只允许一个试用请求，需要两次成功回到可用。

本轮首次 403 后，紧邻流式请求在网关就被跳过，说明“启用”不代表“当前允许请求”。这不等于账号永久损坏，也不应让用户反复开关账号猜测。

测试成功不再自动清除运行时冷却；恢复按钮只是放开业务试用，不发送测试请求。再叠加第 1 项，用户既看不到真实状态，也不能通过现有按钮恢复，反馈缺乏可操作性。

403 的原始文本不足以证明 API Key 失效或模型不存在，当前 `model_error` 的归类过宽。冷却本身是策略，不应一概取消；应区分凭据失效、模型不可用、网络/网关拒绝、限流及请求参数错误。

## 3. 账号测试：截图错误已原样复现

代码：`transport/upstream_connectivity.go`、`cmd/server/ai_modules.go`、`transport/client.go`。

调用相同账号配置的实际 `runUpstreamAccountTest`：HTTP 200，最终仍为 POST `/v1/responses`，Content-Type `text/plain; charset=utf-8`，29 字节正文：

```
Hi! What can I help you with?
```

解析器期待 Responses JSON，产生与截图一致的 `invalid character 'H' looking for beginning of value`。不是 Go 随机解析失败，也不能仅因 HTTP 200 判定 Responses 协议正常。本次未观察到重定向到其他路径。

另外用受控响应验证：合法 SSE 会报字符 `e` 的 JSON 解析错误；HTTP 200 携带 JSON error 会退化为“没有文本”，丢失上游具体错误。

测试固定非流式、64 个输出 token，用独立 `http.Client{}`；真实请求使用业务 transport、代理选择及客户端请求头。两条 HTTP 路径在 v17 已存在，不能归咎于 v18 新增。当前问题是：测试不能代表实际流式链路，错误展示又没有说明协议或响应类型。输出预算对推理模型也偏小，但本次 H 错误不是由输出预算证明导致的。

管理端 POST 接口本地返回了“需要近期重新认证”；为避免改变认证策略，本次真实诊断通过临时测试调用同一个内部函数，没有修改认证中间件，也没有通过管理接口更新账号健康状态。

修复方向：测试复用业务请求构建和出站客户端，支持与业务一致的流式模式；明确展示 HTTP 结果、响应类型、协议验证及脱敏错误。纯文本不能伪装成标准 Responses 成功。

## 4. 首字耗时：口径和单位两个问题

代码：`serving/execute_attempt.go`、`serving/execute_reported_stream.go`、`features/ai/usage/recordPresentation.ts`。

真实成功请求：

- 网关首次响应日志 `first_byte_ms=66333`。
- 请求记录 `total_ms=66334`。
- 请求记录 `first_token_ms=6843`。

每次尝试清零 `FirstTokenMs`，流式处理从最后一次 `transportStartedAt` 计算首个语义输出。前面失败上游的等待及网关准备不计入，但页面只叫“首”，与用户等待时间不一致。按最终尝试计时在 v17 已存在；v18 明确增加重试清零，v19 使用记录表格暴露此指标。

前端 `ms` / `compactMs` 始终四舍五入后拼接 ms，没有秒、分钟转换，且测试明确期待 `6,172ms`。截图 100665ms 应显示约 1 分 40.7 秒；数值大本身不能证明后端把单位放大了 1000 倍。

修复方向：分别保留请求级首个有效输出耗时和尝试级延迟，用准确标签展示，统一格式化为 ms / 秒 / 分钟。错误帧、心跳、生命周期事件不能当成首字。

## 修复与本地验收（后续执行）

按用户要求不保留旧格式兼容读取：Lua 统一省略空历史字段，Go 继续按固定结构读取；旧数据通过独立的一次性清理脚本处理，不在请求中兜底。账号状态读取按资源隔离并记录后台错误，单个损坏状态不会污染全部账号。

其他修复：普通、无明确认证/模型错误码的 403 使用瞬时失败阈值，不再一次拒绝就立即冷却；明确认证/模型/限流错误仍保持原分类。诊断和业务复用 HTTP 出站传输及代理选择，OpenAI/Anthropic 对话测试发送流式请求并验证完整终止；错误、非 JSON/SSE、提前断流、损坏帧均不能判为成功。增加可读 HTTP 错误说明。

首字计时改为从请求入口计算，单次上游延迟独立保留用于评分；空文本事件不计为首字。使用记录、测试结果和稳定性延迟统一使用毫秒/秒/分钟展示，恢复按钮明确标注为“允许立即重试”。
